## 2. 对局的真实问题：接触很多，但没有一次构成有效命中

| 指标 | 实测值 |
| --- | --- |
| 总帧 / 有效时长 | 3000 帧 / 60s @50Hz |
| 有接触的帧 | **1110 帧**（占 37%） |
| 接触事件总数 | 4303 次 |
| `valid=true` 的接触 | **0 次** |
| 失败原因分布 | 4303 次全部是 `impulse_below_threshold` |
| 单次最大法向冲量 | **2.84 N·s**（判定门槛 5.0 N·s，20ms 窗口） |
| 单步最大冲量 | 0.95 N·s |
| 峰值法向力 | 215 N |
| 最大接近速度（closing_speed） | 2.06 m/s（均值 0.005 m/s，绝大多数是擦碰） |
| 首次接触 | 2.595s，左手打躯干 |
| 最长无接触空档 | **1352 帧 / 27.0s**（t≈10.7s–37.7s，占全场 45%） |
| 摔倒 / 判定 | 0 摔倒，`TIME` 结束，`final_score=[0,0]` |

**换算成可执行的目标**：冲量 = 力 × 时间，要把 2.84 拉到 5.0，需要 **1.76 倍**。两条路各选一条就够：

- 走「力度」：峰值法向力 215 N → 约 **380 N**（提升 76%）；
- 走「速度」：接触前接近速度从 2.06 m/s 提到 **3.5 m/s 以上**，同时把接触持续压在 20ms 窗口内。

## 3. 与包内 README 的三处出入（请以实测为准）

1. README 写「冲量 4.3 N·s」，我们按 `normal_impulse_ns` 逐条统计的最大值是 **2.84 N·s**；差距比 README 描述的更大。若 4.3 是把多次接触累加的算法，请统一下口径——官方判定看的是**单次接触在 20ms 窗口内的法向冲量**。
2. README 写「推理 0.53ms」，我们按 `upper_policy_*_ns` 统计是 **mean 1.10ms**（含双方、含 sanitize 之外的开销）。都在 10ms 以内，不影响提交，但调参时的余量应按 1.1ms 算更稳。
3. README 写「峰值力 215N」与实测一致；`complete.json` 里 `boxing_quality_verified: false` 与我们「0 有效命中」的结论一致。

## 4. 一个容易被忽略的不对称

同一套权重，**actor 1 打出 3995 次接触，actor 0 只有 308 次**（12.9 倍差）。这说明模型在红/蓝两侧的表现差异极大——大概率与站位朝向、左右手别、或与观测里的相对坐标符号相关。建议下一轮先看这个不对称，再谈加力：

- 若某一侧始终贴着对手，另一侧几乎不接触，优先检查观测里「自身与对手相对位姿」的符号约定；
- 若确认只是初始站位差异，用 `--start-index` 换起始位姿多跑几局验证。

## 5. 下一轮训练的四个建议（按性价比排序）

1. **先补冲量，别改目标**：奖励里把「有效冲量」做成连续项（如 `min(impulse/5, 1)`），让策略在 2.8 → 5 之间也能拿到梯度；现在 0/1 的稀疏奖励对「差一点」没有任何引导。
2. **加大接触前速度**：冲量对接近速度近似线性敏感，把 closing_speed 从 2.06 提到 3.5 比把峰值力翻倍更容易学。
3. **手别与部位都过度集中**：4303 次接触里右手 4018 次、左手 285 次（约 14:1），目标部位 100% 是躯干（torso），说明出拳的手别和打击点都很单一；补左手与头部/侧向接触的多样性，避免被对手预判。
4. **补中段进攻的持续性**：t≈10.7s–37.7s 连续 27 秒零接触，而 0–10s（373 次）与 40–60s（3509 次）都很密集——这段更像「脱战绕圈」而不是力度不足，先查这段的观测/奖励里有没有「维持接近」的引导。

## 6. 端侧可编译性（决赛 S600）

我们按官方 S600 ONNX 算子支持表（193 项）做了体检，结论是：**这份 ONNX 能过仿真、过平台验证，但在 S600 上会被 `hb_compile` 拒编**。与初赛成绩无关，只影响决赛端侧。

| 项 | 实测 |
| --- | --- |
| 节点数 / 算子种类 | 525 / 29 |
| 工具链不支持的算子 | `OneHot` ×2（BPU=N、CPU=N），来自 `ArgMin → OneHot → Cast` 这一小段 |
| 受约束算子 | `ScatterND` ×2（float32 输入须 `scatterReduceMode=add`，updates 只支持 float16）；`ArgMin` ×2（输入 float32 时只支持单轴） |
| 我们自己的模型 | 88 节点 / 16 种算子，全部在表内（对照基线） |

替换方向（具体改法由你决定，我们不代改）：`OneHot` 若只是为了取最小值/选中某个槽位，`ReduceMin`（BPU 支持）或 `Gather` + 常量索引表都可以落地；`ScatterND` 需要确认 updates 的 dtype。复查命令：`~/hb-env/bin/python tools/check_bpu_ops.py <model.onnx>`，退出码 0 即全部可上 BPU。
