## 1. 目标与规则约束

### 1.1 目标

在初赛截止（2026.12.03）前进入排行榜**前 16 名**，获得决赛资格。

### 1.2 规则约束（来自比赛详情）

| 约束 | 数值 | 工程含义 |
| --- | --- | --- |
| 提交窗口 | 每日 10:00–18:00（北京时间） | 自动化脚本需按此校正时钟 |
| 每日尝试 | ≤ 3 次 | 每次都要当「最后一次」对待 |
| 成功锁定 | 一次验证成功后当天不再接受新提交 | 当日成功后不要再上传 |
| 累计成功 | ≤ 20 次 | 需规划提交节奏，避免前期耗尽 |
| 对战安排 | 18:00 验证截止后统一安排 | 提交必须早于 18:00，建议 17:00 前 |
| 结果公布 | 最早次日 10:00 | 复盘节奏按「T+1」安排 |
| 每策略最少场次 | ≥ 15 场/日 | 保证 Elo 充分更新 |

> 注意：详情页「正式评测次数限制为 5 次」属于赛题一，不适用于赛题二。

## 2. 提交流程

```
本地最终检查（阶段三全流程）
        │
        ▼
上传 .onnx 到平台初赛页面
        │
        ▼
平台校验：格式 / 大小 / 接口 / 推理速度
        │
   ┌────┴────┐
   ▼         ▼
 通过       失败
   │         │
   │         └─► 记录失败原因，修正后重新提交（计入次数）
   ▼
当日锁定，18:00 后统一对战
        │
        ▼
次日 10:00 查看结果、Elo、回放
```

### 2.1 提交时间线（单日）

| 时间 | 动作 |
| --- | --- |
| 10:00 | 确认当日要提交的模型版本 |
| 10:00–16:00 | 最后一次本地校验 + 对战抽检 |
| 16:00–17:00 | 上传并等待验证 |
| 17:00–18:00 | 处理验证异常（如需重试，最多剩 2 次） |
| 18:00 后 | 平台安排对战，本地整理记录 |
| 次日 10:00 | 查看结果与回放，开始复盘 |

## 3. 提交前检查清单

> 每天 3 次尝试、成功一次即锁定当日、累计 20 次成功。顺序按「先本地、再上传、后确认」排列。

### 3.1 硬性检查（缺一不可）

- [ ] 文件是单个 `.onnx`，权重全部内嵌（无 external data）
- [ ] 输入名 `obs`，float32，`[1,1097]`
- [ ] 输出名 `target_pose`，float32，`[1,225]`
- [ ] 文件大小严格 < 50,000,000 字节
- [ ] 官方 `--validate` 通过（本地自研脚本通过不算）
- [ ] 完整链耗时明显低于 10ms（平台按 10ms 判定；官方 bench 的 5ms 只是本地参考）
- [ ] 本地对战至少 10 局，无异常倒地/NaN
  - 本机 16GB 内存跑不动镜像对局时：torch 原生 20 局 + 在 ≥24GB 机器补镜像 10 局，记录里标 `BLOCKED` 而非 `PASS`

### 3.2 版本检查

- [ ] 文件命名含版本号与日期，如 `policy_v7_20261120.onnx`
- [ ] 与训练记录、导出日志可对应
- [ ] 保留上一版成功模型（回滚用）

### 3.3 上传操作检查（当日）

- [ ] 时间在 10:00–18:00 之间，**建议 17:00 前完成上传**（排队与验证都要在 18:00 前结束）
- [ ] 平台页面已登录，队伍信息正常
- [ ] 当前无其他模型在验证中（验证期间不能提交其他模型）
- [ ] 当日尝试次数未用尽（≤3 次/天），累计成功次数距 20 次上限仍有余量
- [ ] 上传后立刻记录：提交时间、文件名、sha256、第几次尝试

### 3.4 提交后确认

- [ ] 盯到「验证成功」而不是「上传成功」，两者都须在 18:00 前完成
- [ ] 失败要归类原因：格式 / 大小 / 接口 / 耗时 / 平台故障（平台故障留截图，可申请退还次数）
- [ ] 当日验证成功即锁定，当天不再上传
- [ ] 次日 10:00 查看 Elo、名次、比赛详情，下载 HDF5 回放
- [ ] 回放 MP4 用 Chrome/Edge 在 localhost/HTTPS 页面导出，导出期间标签页保持可见

### 3.5 次数预算

- [ ] 每轮提交前算一遍：剩余成功次数 − 计划提交次数 ≥ 3 的缓冲
- [ ] 优先验证成功率高的稳模型，不为小改动烧次数
- [ ] 12.03 截止前预留最后 2–3 次给冲刺版本

### 3.6 最容易踩的五个坑

1. 17:30 才上传：排队与验证可能超出 18:00，验不完同样消耗次数。
2. 验证成功当天再上传：当日已锁定，新模型只会被拒。
3. 拿没跑官方 `--validate` 的模型上：本地自研脚本通过不等于平台通过。
4. 混用耗时阈值：官方 bench 的 `mean ≤ 5ms` 是本地参考，平台按 10ms 判定，但别把模型做到贴着 10ms。
5. 失败后慌乱连传：当日锁定后等次日再修，连续试错只烧尝试次数。

## 4. 结果复盘方法

### 4.1 数据来源

| 来源 | 内容 |
| --- | --- |
| 排行榜 | Elo、名次、对手 |
| 比赛详情 | 单场比分、命中数、KO 情况 |
| HDF5 轨迹 | 完整回放，可播放/跳转/导出 MP4 |

### 4.2 复盘表模板

| 场次 | 对手 Elo | 我方得分 | 对方得分 | 结果 | 关键事件 |
| --- | --- | --- | --- | --- | --- |
| 1 | — | — | — | 胜/负/平 | 被 KO / 连续命中 / 倒地 |
| 2 | — | — | — | — | — |

### 4.3 归因分类

| 归因 | 现象 | 对策 |
| --- | --- | --- |
| 进攻不足 | 得分低、出拳少 | 提高命中奖励、增加出拳频率约束 |
| 防守薄弱 | 被连续命中 | 提高被命中惩罚、加入闪避奖励 |
| 平衡差 | 频繁倒地 | 加强站姿奖励、平滑输出 |
| 时序错位 | 总慢半拍 | 检查输出窗口 T 与平滑系数 |
| 泛化差 | 对某类对手必败 | 增加对手多样性训练 |
| 过度保守 | 全程站桩 | 提高 entropy、缩短单局训练时长 |

### 4.4 回放分析要点

1. 先看**开局 5 秒**：是否站稳、是否主动接近；
2. 再看**首次交火**：出拳时机、距离控制；
3. 重点看**失分片段**：是防守漏洞还是平衡问题；
4. 最后看**终局**：领先/落后时行为是否合理。

## 5. Elo 迭代策略

### 5.1 Elo 机制要点

| 项 | 说明 |
| --- | --- |
| 初始分 | 每日重置为 1500 |
| 更新依据 | 当日对战结果 + 对手等级分 |
| 不受影响 | KO 奖励分、单场比分差 |
| 排名 | 按最后一日排行榜前 16 名晋级 |

**推论**：击败高分对手收益更大；因此「能稳定赢中高分对手」比「大比分虐低分对手」更有价值。

### 5.2 提交节奏建议

| 阶段 | 策略 |
| --- | --- |
| 早期 | 快速验证链路，提交「能跑通」的版本，积累对战样本 |
| 中期 | 每次提交前确保本地胜率有提升；避免提交未验证的大改 |
| 后期 | 冻结架构，只做小幅调参；保留 2–3 次成功提交额度 |
| 截止前 | 不再冒险，确保最新验证成功模型就是最优版本 |

### 5.3 反模式

| 反模式 | 后果 |
| --- | --- |
| 每日三次全用在大改上 | 失败次数耗尽，当日无有效模型 |
| 截止前 30 分钟才提交 | 验证排队超时，消耗次数且当日无成绩 |
| 只提交不分析 | 盲目迭代，Elo 停滞 |
| 频繁更换架构 | 无法定位涨跌原因 |

## 7. 异常处理

| 异常 | 处理 |
| --- | --- |
| 上传超时/网络中断 | 重试上传；确认是否已计入次数 |
| 验证失败（接口不符） | 回查阶段三的结构检查，修正后重提 |
| 验证失败（超时/耗时超标） | 减层/融合，重新基准后再提交 |
| 页面显示成功但无对战结果 | 等待人工复核，次日 10:00 再看 |
| 平台故障 | 保留截图与日志，按规则申请退还次数 |
| 提交后才发现模型有缺陷 | 当日已锁定无法改；次日优先修复，勿慌乱连续提交 |

## 8. 本地预检入口

```bash
python3 tools/verify_phase4.py --onnx models/policy_v{N}_{YYYYMMDD}.onnx \
  --json outputs/verify/phase4.json
```

| 检查 | 对应门禁 | 本地可否判定 |
| --- | --- | --- |
| 命名符合 `policy_v{N}_{YYYYMMDD}.onnx` | G4-03 | ✅ |
| 保留至少 1 个可回滚成功模型 | G4-06 | ✅ |
| 连续本地对战 ≥ 10 局无异常 | G3-07 复检 | ✅（需镜像） |
| 提交记录 / 复盘记录齐备 | G4-04 / G4-05 | ✅（检查文件存在） |
| 平台验证通过 | G4-01 | ❌ `BLOCKED`，仅平台可判 |
| 排行榜名次 | G4-07 | ❌ `BLOCKED`，仅平台可判 |

**表述规则（审查文档 4.5）**：本地脚本只能输出「预检通过」。G4-01、G4-04、G4-05、G4-07 的实际结论由平台产生，**禁止把本地预检写成"验证通过"**。无平台账号或不在提交窗口时，这些条目必须记为 `BLOCKED`。
