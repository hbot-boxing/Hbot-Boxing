## 1. 目标与约束

### 1.1 目标

训练出一个能同时完成**进攻、防守、保持平衡**三个子任务的策略，且在本地双模型对战中具备稳定表现。

### 1.2 硬约束（来自架构文档第 5 章）

| 约束 | 数值 | 对设计的直接影响 |
| --- | --- | --- |
| 模型文件 | < 50,000,000 字节 | float32 参数量上限约 12.5M |
| 完整链推理 | ≤ 10ms（RTX 5090） | 上层推理需显著低于 10ms，为 HoloMotion 留余量 |
| 输入 | `obs` float32 `[1,1097]` | 网络第一层固定 1097 |
| 输出 | `target_pose` float32 `[1,225]` | 网络最后一层固定 225 |
| 决赛设备 | RDK S600 | 避免使用端侧不友好算子（如大 kernel 卷积、复杂 attention） |

**推理耗时预算（建议分配）**：

| 环节 | 预算 |
| --- | --- |
| 上层策略前向 | ≤ 3ms |
| 数据搬运/格式转换 | ≤ 1ms |
| HoloMotion 2.0 | 余量（约 5–6ms） |

> 该分配为工程估计，最终以平台 RTX 5090 实测为准。

### 1.3 验收标准（对应审查文档第三章 G2、第四章 4.4）

| 门禁 | 条件 | 判定方式 | 本阶段可自证 |
| --- | --- | --- | --- |
| G2-01 | `src/models/policy.py` 存在，I/O 尺寸 1097→225 | 构造随机输入断言 | ✅ |
| G2-02 | 训练可收敛，≥ 1 个 checkpoint 本地对战无异常倒地 | rollout 日志 | ✅（不导出） |
| G2-03 | 预处理与推理适配器为同一份实现（`import`，非复制） | 代码审查 | ✅ |
| G2-04 | 奖励函数调用官方判定器，无自建近似规则 | 代码审查 | ✅ |
| G2-05 | 每个 checkpoint 对战 ≥ 20 局 | 日志统计 | ✅ |
| G2-06 | 参数量估算 ≤ 12.5M | 代码计算 | ✅ |
| G2-07 | torch 原生 rollout ≥ 20 局，官方判定器输出，**不依赖 ONNX 导出** | 评测日志 | ✅ |
| G2-08 | `tools/verify_phase2.py` 可运行 | 退出码 + JSON | ✅ |

**关键约束（C-10 / C-11）**：本阶段验收**不得**依赖阶段三导出的 ONNX。对战能力由 7.1 的 torch 原生 rollout 提供；ONNX 格式合规、推理链耗时、镜像 `--validate` 才属于阶段三。

## 2. 网络结构设计

### 2.1 选型矩阵

| 架构 | 参数量估算 | 前向耗时 | 时序建模 | 推荐场景 |
| --- | --- | --- | --- | --- |
| MLP 3–5 层 | 0.5–3M | < 1ms | 无（靠拼帧） | 首版 baseline、快速闭环验证 |
| MLP + 残差 + LayerNorm | 3–8M | 1–2ms | 无 | 主线候选 |
| 1D CNN（3–5 层） | 1–5M | 1–2ms | 局部时序 | 需要短时动作连续性 |
| Transformer 2–4 层（d=128–256） | 3–10M | 2–4ms | 强 | 需要对手行为建模，但要控层数与头数 |

**参数量核算公式**：

```
MLP:  sum(in_i * out_i + out_i)
Conv1D: sum(k * c_in * c_out + c_out)
Transformer: 每层 ≈ 4 * d^2 (attn) + 8 * d^2 (ffn)
```

导出后文件大小 ≈ 参数量 × 4 字节（float32），需严格小于 50,000,000 字节，**建议控制在 40MB 以内留 buffer**。

### 2.2 推荐结构（主线）

```
输入 obs [1,1097]
      │
  LayerNorm
      │
  Linear 1097→512 + GELU
      │
  Residual Block × 2  (512, LayerNorm, GELU)
      │
  Linear 512→256 + GELU
      │
  Linear 256→225
      │
输出 target_pose [1,225]
```

估算参数量：

| 层 | 参数量 |
| --- | --- |
| 1097→512 | 562,176 |
| 512→512 ×2（含残差） | 524,800 ×2 |
| 512→256 | 131,328 |
| 256→225 | 57,825 |
| 合计 | ≈ 1.80M（约 7.2MB） |

余量充足，可在此基础上加深或加宽。

### 2.3 时序建模方案

观测中已含「历史状态缓存」，两种用法：

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| 拼帧展平 | 直接把历史帧拼进 1097 维，用 MLP | 简单；但无法区分时间顺序 |
| 显式时序编码 | 把历史拆成 `[T_hist, D]`，过 GRU/Conv1D 后与当前帧融合 | 表达强；导出与端侧兼容需验证 |

**建议**：先用拼帧 MLP 跑通，再评估是否值得引入时序模块。

## 3. 输入输出处理

### 3.1 输入预处理（对应架构 5.2）

| 步骤 | 说明 |
| --- | --- |
| 归一化 | 用官方统计量对每段字段做 z-score；无统计量时先用运行中采集的均值/方差 |
| 异常值裁剪 | 对速度类字段做 ±5σ 裁剪，防止数值爆炸 |
| 历史拼接 | 按固定顺序拼接，训练与推理必须完全一致（写入配置，禁止手改） |

> **一致性红线**：训练时的预处理代码与推理时的适配器必须是同一份实现（直接 import），禁止复制两份。

### 3.2 输出后处理（对应架构 5.3）

| 步骤 | 说明 |
| --- | --- |
| 值域裁剪 | 按官方位姿范围 clip |
| 平滑 | 一阶低通 `y_t = α·y + (1-α)·y_{t-1}`，α 建议 0.2–0.4 |
| 残差模式（可选） | 若官方接口支持，输出相对当前位姿的偏移，可降低学习难度 |

**训练期注意**：平滑会改变输出分布，训练时应把平滑也放进可微链路（或训练后用同一平滑做评测），避免训练/推理不一致。

## 4. 训练架构

### 4.1 总体链路（对应架构 3.2）

```
多个仿真环境实例（并行对战）
        │  (obs, target_pose, reward, next_obs, done)
        ▼
   经验回放池
        │  采样 batch
        ▼
   策略网络 + 价值网络
        │  梯度更新
        ▼
   checkpoint ──► 定期导出 ONNX 做本地对战评估
```

### 4.2 训练算法选择

| 算法 | 适用 | 说明 |
| --- | --- | --- |
| PPO | 主线 | on-policy，稳定，适合连续动作空间 |
| SAC | 备选 | off-policy，样本效率高，超参更敏感 |
| 行为克隆（BC） | 冷启动 | 用规则/脚本策略生成示范数据，先学会基本站立与出拳 |
| BC + RL 混合 | 推荐 | BC 提供初始策略，RL 提升对抗性 |

### 4.3 并行与吞吐

| 项 | 建议 |
| --- | --- |
| 环境并行数 | 依据 GPU 显存与 CPU 核数，先 8–16 路 |
| 单局时长 | 60s（与比赛一致），训练期可缩短到 20–30s 加速迭代 |
| 更新频率 | 每 N 步（N 与 rollout 长度匹配）做一次梯度更新 |
| checkpoint | 每 30 分钟或每 100 次更新保存一次，保留最近 5 个 |

### 4.4 课程学习（推荐）

1. **静止对手**：学会稳定站立、出拳命中固定目标；
2. **慢速移动对手**：学会追踪与基础防守；
3. **完整对手（baseline 策略）**：学会对抗与平衡；
4. **多对手混合**：提升泛化，避免过拟合单一打法。

## 5. 奖励函数

### 5.1 奖励项（对应架构 3.2 表格）

| 维度 | 触发条件 | 建议奖励 | 说明 |
| --- | --- | --- | --- |
| 命中 | 手部接触对手头部/躯干且满足 5N·s/20ms | +1.0 | 与比赛计分对齐 |
| 重复命中约束 | 同手 200ms 内重复 | 不重复给分 | 与规则一致，防止刷分 |
| 被命中 | 自身头部/躯干被有效击中 | −0.5 ~ −1.0 | 权重可调，避免只攻不守 |
| 平衡 | 骨盆/躯干高度 ≥ 0.30m | 每步小正奖励 | 鼓励维持站姿 |
| 倒地 | 高度 < 0.30m | 大负奖励 | 强约束，防摆烂 |
| KO | 对手连续倒地 3s | +10.0（对应 1000 分的缩比） | 终结信号 |
| 被 KO | 自身连续倒地 3s | −10.0 | 终结信号 |
| 时间/分差 | 剩余时间、当前分差 | 小权重塑形 | 引导领先时控场、落后时进攻 |

### 5.2 奖励工程注意事项

1. **量级统一**：所有项缩放到同一量级（建议主项在 ±1 附近），避免梯度被大项主导。
2. **终结奖励稀疏**：KO 稀有，需配合过程奖励（命中、平衡）做稠密化。
3. **防奖励作弊**：检查策略是否通过「贴身乱打」「假倒地」获取奖励，必要时加动作能耗惩罚。
4. **与规则对齐**：脚击不得分、冲量不足不得分，训练环境应使用官方判定器，避免自建近似规则导致迁移失败。

### 5.3 参考实现骨架

```python
def compute_reward(self, prev, cur, events):
    r = 0.0
    r += 1.0 * events.hit_landed            # 有效命中
    r -= 0.8 * events.hit_taken             # 被命中
    r += 0.05 if cur.pelvis_height >= 0.30 else -2.0
    r += 10.0 * events.ko_win
    r -= 10.0 * events.ko_lose
    r += 0.1 * (cur.score_diff - prev.score_diff) * 0.1   # 分差塑形（小权重）
    return r
```

> 具体事件字段以官方环境接口为准；上表权重为起点，需通过本地对战调参。

## 6. 训练配置与超参

### 6.1 配置文件示例

```yaml
train:
  algo: ppo
  total_steps: 20_000_000
  rollout_len: 4096
  num_envs: 16
  gamma: 0.99
  gae_lambda: 0.95
  clip_range: 0.2
  lr: 3.0e-4
  entropy_coef: 0.01
  value_coef: 0.5
  max_grad_norm: 0.5

model:
  hidden: [512, 512, 256]
  activation: gelu
  layernorm: true

reward:
  hit_landed: 1.0
  hit_taken: -0.8
  balance_bonus: 0.05
  fall_penalty: -2.0
  ko_win: 10.0
  ko_lose: -10.0
```

### 6.2 调参顺序建议

1. 先固定奖励，调 `lr` 与 `entropy_coef`，让策略先学会「不倒地 + 会出拳」；
2. 再调 `hit_taken` 权重，控制攻防平衡；
3. 最后调分差塑形权重，避免过早追求比分而牺牲稳定性。

## 7. 本地评测指标

每轮 checkpoint 都要跑一次本地对战，记录以下指标：

| 指标 | 计算方式 | 目标 |
| --- | --- | --- |
| 胜率 | 对 baseline 的胜场 / 总场 | 稳步上升 |
| 平均得分 | 每局得分 | 上升 |
| 被击中率 | 被有效命中次数 / 60s | 下降 |
| 倒地率 | 倒地局数 / 总场 | 接近 0 |
| KO 率 | KO 胜场 / 总场 | 上升 |
| 动作平滑度 | 输出相邻帧差分的均值 | 不宜过大 |

> 单局样本噪声大，每个 checkpoint 至少跑 20 局再下结论。

### 7.1 torch 原生 rollout 自证（替代 ONNX 对战）

审查文档 C-11 要求：阶段二不导出模型也能完成对战评测，避免与阶段三形成循环依赖。

```bash
python3 tools/verify_phase2.py \
  --ckpt outputs/train/ckpt_1000000.pt \
  --episodes 20 \
  --json outputs/verify/phase2.json
```

做法要点：

1. 模型保持 `eval()`，输入用 `obs_adapter` 的真实输出（不是随机张量）；
2. 动作经过 `action_adapter` 的裁剪与平滑后直接送入 HoloMotion，**不经过 ONNX**；
3. 判定完全依赖官方判定器返回的 `hit / fall / score / remaining_time`，禁止自建近似规则（C-04）；
4. 每局结果写 `outputs/eval/train_eval_{ckpt}.csv`，字段与 §7 指标表一致；
5. 退出码：全部 20 局跑完且指标落盘为 `0`；仿真未就绪为 `2` 并把各项记 `BLOCKED`。

与 `run.sh --match` 的区别：本路径**不测**推理链耗时、不测格式合规、不产出 `.hdf5` 回放——这些属阶段三，不在本阶段验收范围内。
