## 一、系统总览

```
+----------------------------------------------------------+
|                    仿真拳台环境                           |
|  +----------+    +--------------+    +----------------+  |
|  | 对手策略  |    |  物理仿真引擎  |    |  比赛规则判定器  |  |
|  | (平台/本地)|    |  (Isaac Sim)  |    | (命中/倒地/KO) |  |
|  +----------+    +------+-------+    +-------+--------+  |
|                         |                    |           |
|                    +----v----+               |           |
|                    | 观测生成  |<--------------+           |
|                    +----+----+                           |
+-------------------------+--------------------------------+
                          | obs [1,1097]
                          v
              +-----------------------+
              |     上层拳击策略       |  <-- 参赛队开发
              |   (ONNX 模型文件)      |
              +-----------+-----------+
                          | target_pose [1,225]
                          v
              +-----------------------+
              |   HoloMotion 2.0      |  <-- 官方提供（固定）
              |   下层运动控制器       |
              +-----------+-----------+
                          | 关节动作
                          v
              +-----------------------+
              |   Unitree G1 机器人   |
              |   (配备拳套，仿真)     |
              +-----------------------+
```

**核心约束**：整个控制闭环中，参赛队只负责上层策略，不允许在推理链路中引入额外的大模型或外部决策编排。

## 二、两层控制架构

### 2.1 上层策略（参赛队开发）

| 属性 | 说明 |
| --- | --- |
| 功能 | 根据观测生成未来短时间内的身体目标位姿序列 |
| 输入 | `obs` float32 `[batch=1, dim=1097]` |
| 输出 | `target_pose` float32 `[batch=1, dim=225]` |
| 格式 | ONNX，所有权重内嵌 |
| 大小 | < 50,000,000 字节 |
| 推理耗时 | 上层 + 下层完整链 <= 10ms（RTX 5090） |

**设计要求**：
- 需同时完成进攻（出拳得分）、防守（闪避/格挡）、保持平衡（防倒地）三项子任务。
- 决策须考虑对手位置与状态，形成动态对抗能力。

### 2.2 下层控制器 HoloMotion 2.0（官方提供）

| 属性 | 说明 |
| --- | --- |
| 功能 | 将上层输出的目标位姿转换为 Unitree G1 关节动作 |
| 输入 | `target_pose` float32 `[1,225]` |
| 输出 | 机器人关节位置/力矩指令 |
| 实现 | 由仿真环境内部调用，参赛队无需关心 |

## 三、数据流

### 3.1 推理时数据流

```
仿真环境 --> 观测生成器 --> obs[1,1097] --> 上层策略 --> target_pose[1,225]
                                                      |
                                                      v
机器人关节 <--- HoloMotion 2.0 <--- target_pose[1,225]
    |
    v
物理仿真步进 --> 更新状态 --> 下一帧观测 --> (循环)
```

观测、推理、动作执行形成**闭环**。上层策略每次输出一个未来短时间窗口的轨迹，下层控制器逐帧转换为关节动作，仿真环境消耗动作后产生新的观测。

### 3.2 训练时数据流

```
+------------+     +------------+     +--------------+
| 仿真环境    |---->| 经验回放池  |---->| 上层策略训练  |
| (多局对战)  |     | (s,a,r,s') |     | (RL/IL 更新) |
+------------+     +------------+     +------+-------+
      ^                                      |
      |            checkpoint                 |
      +--------------------------------------+
```

**奖励函数设计要点**：

| 奖励维度 | 信号来源 |
| --- | --- |
| 进攻 | 有效命中对手头部/躯干 +1 分（需满足 5N.s/20ms 冲量） |
| 防守 | 不被对手命中；维持有利站位 |
| 平衡 | 骨盆/躯干高度 >= 0.30m，避免倒地 |
| 终结 | 击倒对手 +1000 分（连续倒地 3s） |
| 比赛 | 分差信号、剩余时间压力 |

## 四、输入／输出接口规格

### 4.1 观测输入 `obs`

| 属性 | 值 |
| --- | --- |
| 名称 | `obs` |
| 数据类型 | `float32` |
| 形状 | `[1, 1097]` |
| 语义 | 三类信息的拼接（详见下文） |

**观测类别分解**：

| 类别 | 大致维度 | 内容 |
| --- | --- | --- |
| 自身状态 | ~N1 | 骨盆、双腕、双踝等身体关键点的 3D 位姿、线速度、角速度，以及历史窗口缓存 |
| 对手信息 | ~N2 | 对手关键身体点相对于自身的 3D 位置（头部、躯干、双腕等），可能含速度 |
| 比赛信息 | ~N3 | 剩余比赛时间（归一化）、双方当前分差 |

> 精确字段划分与坐标系定义见官方 HoloMotion 接口文档（[GitHub](https://github.com/HorizonRobotics/HoloMotion/tree/master/holoboxing)）。

### 4.2 动作输出 `target_pose`

| 属性 | 值 |
| --- | --- |
| 名称 | `target_pose` |
| 数据类型 | `float32` |
| 形状 | `[1, 225]` |
| 语义 | 未来短时间窗口内机器人身体关键点的目标位姿序列 |

**输出结构推断**：
- 时间窗口 T 帧 × 关键点数量 K × 位姿维度 D（如 T=15, K=15, D=1 或类似组合）
- HoloMotion 2.0 根据此轨迹生成逐帧关节动作

> 精确输出格式（帧数、关键点顺序、坐标系）见官方接口文档。

## 五、模型设计指南

### 5.1 架构选型空间

赛事**不对 Policy 架构做限制**，但有以下硬约束：

| 约束 | 影响 |
| --- | --- |
| 文件 < 50MB | 参数量上限约 **12.5M**（float32） |
| 完整链 <= 10ms | 上层推理需控制得更低（为 HoloMotion 预留时间） |
| RTX 5090 实测 | 本地 4090 结果不作为验收依据 |
| 端侧部署（决赛） | 需能在 RDK S600 上运行 |

**候选架构对比**：

| 架构 | 参数量 | 推理速度 | 表达能力 | 端侧友好 |
| --- | --- | --- | --- | --- |
| 浅层 MLP (3-5层) | 低 | 极快 | 有限 | 是 |
| 深层 MLP + 残差 | 中 | 快 | 中等 | 是 |
| Transformer (2-4层) | 中 | 中等 | 强（时序建模） | 取决于实现 |
| CNN 1D | 低-中 | 快 | 中等 | 是 |

**建议路径**：
1. 先用 MLP 快速验证端到端链路
2. 逐步增加架构复杂度，在本地对战中对标 baseline
3. 导出 ONNX 后用 `--benchmark` 确认推理耗时

### 5.2 输入预处理

- 观测归一化：按官方提供的统计量（均值/方差）标准化
- 历史状态拼接：将多帧历史按时间维度展平或做时序编码
- 可选：手工特征工程（对手距离、攻击角度、倒地风险等）作为辅助输入

### 5.3 输出后处理

- 确保 `target_pose` 值域不超出 HoloMotion 接收范围
- 对关键点做平滑约束（避免突跳导致仿真不稳定）
- 可选：输出残差（相对于当前位姿的偏移量）

## 六、ONNX 导出与管线

### 6.1 导出流程

```
PyTorch / TF 模型
       |
       v torch.onnx.export / tf2onnx
ONNX 模型（含权重）
       |
       v 验证
+-- 输入输出形状检查: obs[1,1097] -> target_pose[1,225]
+-- 文件大小检查: < 50,000,000 字节
+-- 推理耗时检查: --benchmark
       |
       v
./holoboxing/run.sh --validate models/xxx.onnx
```

### 6.2 导出注意事项

| 事项 | 说明 |
| --- | --- |
| opset 版本 | 应与平台 ONNX Runtime 版本兼容（建议 opset >= 13） |
| 动态维度 | 固定 batch=1（`[1,1097]` / `[1,225]`），避免动态 shape |
| 算子覆盖 | 避免使用 ONNX Runtime 不支持的算子；优先使用标准算子 |
| 精度 | float32 即可，初赛不要求量化 |
| 大小 buffer | 导出后检查字节数，确保严格 < 50,000,000 |
