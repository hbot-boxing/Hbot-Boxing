# 联合排查反馈：atk6 v3（2026-11-05）

**结论：交付件合规可提交，本机验收 PASS（受限）；但本机完整链 5.36ms 比同机 v1 的 4.29ms 慢 25%，原因是节点数 88 → 227，不是模型变大。对局层面冲量质量确有提升，左手 0 命中与 0.85m 贴身距离仍未解决。**

数据来源：`atk6-v3-20261104.tar.gz`（29,266,761 字节、19 条目 / 18 个文件，tarball sha256 `870fa5b3a80d2ee8c911e10865ad479502482be84bae59a7182f7f9ce72a21c0`）、包内 `model.onnx`、`match.json`（3000 帧）、`validation.json`、`benchmark.json`、`ops-check.json`、`SHA256SUMS.txt`。

## 3. 本机测速：预热复测与同机对照

| 运行 | 条件 | mean_ms | p50 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| 冷启 | 首次加载后立即测 | 5.363 | 5.267 | 6.406 | 6.549 |
| 预热一 | 同进程连续第二次 | 5.379 | 5.327 | 6.298 | 6.623 |
| 预热二 | 同进程连续第三次 | 5.528 | 5.438 | 6.576 | 6.620 |
| 同机对照 | v1，5,135,076 字节 / 88 节点 | **4.285** | 4.247 | 5.067 | 5.164 |

结论：

1. **预热没有变快，反而略慢**——5.4ms 是本机真实水平，不是冷启假象。
2. 官方 `chain_benchmark` 内置判据是 `mean ≤ 5.0ms`，本次 payload `passed=false`；平台实际按 10ms 判。达标，但余量只有 1.87 倍（v1 是 2.33 倍）。
3. **体积减半却慢了 1.07ms**：v3 少了 2.79MB 权重，多了 139 个节点（Slice×41、Clip×18、ReduceL2×16、Concat×19、Div×18、Where×8、Expand×8、Gather×4）。摊到每节点约 7.7µs，是 GPU 上逐节点 launch 开销的量级，不是算力瓶颈。所以要拉回余量，只能减节点，不能靠"模型变小"。

注意：包内 3.878ms 是另一台机器的读数（驱动 595.99，本机 580.17），与 5.36ms 不可直接比较；同机对照的 4.29ms 才是可比基线。

## 4. 冲量口径（本轮重点）

官方判定口径（来自 `match.json` 的 `scoring_version` / `scoring_config`）：

| 项 | 口径 |
| --- | --- |
| 计分部位 | 仅手部接触对方头部或躯干；脚击不计分 |
| 判定窗口 | 每只手最近 **20ms** |
| 门槛 | 该窗口内法向冲量 ≥ **5.0 N·s** |
| 左右手 | 独立计分，同手两次计分间隔 ≥ **200ms** |
| 冲量复用 | 已计分的冲量不可重复使用（`consume_scored_impulse: true`） |
| 版本标识 | `hands_only_normal_impulse20ms_5Ns_cooldown200ms_fall030_ko1000_v6` |

我方统计口径（`tools/analyze_match.py`）：取**单次接触**的 `normal_impulse_ns`，不跨窗口累加、不合并多次接触；P50/P90 是对这些单次值取分位数。这条口径和官方判定一致——差别在于我们统计全部接触，官方只对满足手部+部位+窗口+冷却条件的接触计分。

**复核状态**：包内 `match.json` 只有 `summary` / `metadata` / `frames`，没有逐次接触事件表。因此 P50 1.13、P90 2.14 这组数字**我方无法复核**，只能记为「A 侧口径」。要复核需要你导出逐次明细：`timestamp_ms, hand, body_part, normal_impulse_ns, scored, blocked_reason`。
