## 一、文档角色与使用规则

### 1.1 定位

本文档独立于阶段文档、架构文档、任务文档。它不是"又一个说明书"，而是 **阶段审查时的 checklist 母本**：

- 每个阶段结束时，对照本文档逐条打勾；
- 未通过的条目阻塞进入下一阶段；
- 已锁定的条目在后续阶段中不得无声修改。

### 1.2 与其他文档的关系

| 文档 | 角色 | 修改策略 |
| --- | --- | --- |
| 比赛详情 | 官方规则来源 | 随官网更新 |
| 任务文档 | 高层里程碑与风险 | 按需修订 |
| 架构文档 | 系统设计原理 | 按需修订 |
| 阶段文档 ×5 | 各阶段工程指南 | 按需修订 |
| **阶段审查文档（本文）** | **契约与门禁定义** | **所有修改必须显式记录，不得无声变更** |

### 1.3 修改规则

1. 任何锁定条目的修改必须经过 **审查流程**（见第八章）；
2. 修改后必须在底部更新日志追加记录，说明原因；
3. 如果修改导致下游阶段文档失效，需同步更新阶段文档。

## 四、独立检验入口

本章解决一个具体问题：**某阶段的代码与配置都写完后，能否只靠该阶段（及其前序阶段）的产物，判定它"通过"**。

### 4.1 定义

**独立检验**：阶段 N 的验收只用「阶段 1..N 的产物 + 该阶段自身的代码配置」即可判定，不依赖阶段 N+1 的任何产出。

不满足这一条的验收项，视为**验收定义缺陷**，必须在审查时修正，而不是"实际做的时候凑合一下"。

### 4.2 统一约定

以下约定对所有阶段生效，编号 V-xx 与 G/S/I/C 同级，违反即为硬阻塞。

| # | 约定 | 锁定值 |
| --- | --- | --- |
| V-01 | 入口脚本路径 | `tools/verify_phase{N}.py`（N = 1..5） |
| V-02 | 调用方式 | `python3 tools/verify_phase{N}.py`；加 `--json <path>` 输出机器可读结果 |
| V-03 | 退出码 | `0` = 全部通过；`1` = 存在阻断项；`2` = 前置依赖缺失（未就绪） |
| V-04 | 检查项映射 | 每条检查输出必须带 `gate` 字段，取值为第三章的 G 编号 |
| V-05 | 结果落盘 | 默认写入 `outputs/verify/phase{N}.json` |
| V-06 | 三态结论 | 每条检查只能是 `PASS` / `FAIL` / `BLOCKED`；**禁止把"无法检查"记为 PASS** |
| V-07 | 依赖声明 | 脚本启动时必须打印其依赖的产物清单与是否就绪 |

### 4.3 自证能力矩阵

| 阶段 | 独立自证 | 允许依赖（仅前序 + 本阶段） | 不可自证部分 | 处置 |
| --- | --- | --- | --- | --- |
| 一 | ✅ 完全 | 官方镜像、HF 资源包、本阶段适配器 | 无 | — |
| 二 | ✅ 完全（补 G2-07 后） | 阶段一环境、本阶段训练代码与 checkpoint | 无（对战能力由 torch 原生 rollout 提供） | 见 4.4 |
| 三 | ✅ 完全 | 阶段二 checkpoint、阶段一镜像 | `--validate` / `--benchmark` / 对战需镜像 | 需 Docker；结构/一致性检查纯 CPU |
| 四 | ⚠️ 部分 | 阶段三 ONNX、平台账号（外部） | G4-01/04/05/07 只能由平台判定 | 降级为「预检」，见 4.5 |
| 五 | ⚠️ 部分 | 阶段三 ONNX、RDK S600 实机（外部） | G5-01..G5-07 依赖待公告接口与实机 | 降级为「预检」，见 4.5 |

### 4.4 阶段二的循环依赖与解法

**问题**：G2-02、G2-05 要求「每个 checkpoint 本地对战 ≥ 20 局」，而对战入口 `run.sh --match` 只接受 ONNX；导出 ONNX 属于阶段三。于是阶段二的验收反向依赖阶段三的产物，形成 2 ↔ 3 循环。

**锁定规则**：

| # | 规则 |
| --- | --- |
| C-10 | 阶段二的验收 **不得**依赖阶段三导出的 ONNX 产物 |
| C-11 | 阶段二必须提供 torch 原生 rollout 评测路径：在训练环境内直接 rollout N 局，用**官方判定器**输出得分/命中/倒地结果，不导出、不转换 |

该路径只允许读取仿真状态与官方判定结果，不得自建近似判定规则（与 C-04 一致）。

### 4.5 不可自证项的表述规则

1. 阶段四的 G4-01、G4-04、G4-05、G4-07 由平台判定，本地最多给出「预检通过」，**禁止写成「验证通过」**。
2. 阶段五在无 RDK S600 实机时，G5-01..G5-07 一律记为 `BLOCKED`，不得记为 `PASS`。
3. 阶段四、阶段五的检验入口（`verify_phase4.py`、`verify_phase5.py`）在依赖缺失时必须以退出码 `2` 结束，并在 JSON 中把对应条目写为 `BLOCKED`。

### 4.6 每阶段检验范围（门禁映射）

| 阶段 | 入口脚本 | 覆盖门禁 |
| --- | --- | --- |
| 一 | `tools/verify_phase1.py` | G1-03、G1-05、G1-06、G1-10（G1-01/02/07 需镜像，由脚本检测后判定 READY/BLOCKED） |
| 二 | `tools/verify_phase2.py` | G2-01、G2-03、G2-06、G2-07、G2-08 |
| 三 | `tools/verify_phase3.py` | G3-01、G3-02、G3-03、G3-04、G3-08、G3-09 |
| 四 | `tools/verify_phase4.py` | G4-03、G4-06、G4-08（其余由平台判定，输出 `BLOCKED`） |
| 五 | `tools/verify_phase5.py` | G5-02、G5-03、G5-06、G5-08（其余依赖实机，输出 `BLOCKED`） |

### 5.1 观测输入 `obs`

```

类型:     float32

内容:     三类信息的拼接
         ├── 自身状态:     关键点位姿/速度/历史
         ├── 对手信息:     对手关键点相对位置/速度
         └── 比赛信息:     剩余时间(归一化)、分差
```

| 字段 | 锁定项 | 锁定值 | 来源 |
| --- | --- | --- | --- |
| I-01 | 名称 | `obs` | 架构文档 §4.1 |
| I-02 | dtype | `float32` | 架构文档 §4.1 |
| I-03 | 形状 | `[1, 1097]` | 架构文档 §4.1 |
| I-04 | 维度顺序 | batch=1, dim=1097 | 架构文档 §4.1 |

```
名称:     target_pose
类型:     float32

```

| 字段 | 锁定项 | 锁定值 | 来源 |
| --- | --- | --- | --- |
| I-08 | 名称 | `target_pose` | 架构文档 §4.2 |

| I-10 | 形状 | `[1, 225]` | 架构文档 §4.2 |

| I-12 | 输出平滑 | 一阶低通 `y_t = α·y + (1-α)·y_{t-1}`，**α ∈ [0.2, 0.4]** | 阶段一 §5.2 |
| I-13 | 平滑一致性 | 训练期平滑放入可微链路或训练后同一平滑做评测 | 阶段二 §3.2 |

### 5.3 ONNX 导出接口

```python
# 导出函数签名（锁定）
torch.onnx.export(
    model,
    dummy,                              # torch.zeros(1, 1097, dtype=float32)
    path,
    input_names  = ["obs"],            # 锁定
    output_names = ["target_pose"],     # 锁定
    opset_version = ≥13,                # 锁定下限
    do_constant_folding = True,         # 锁定
    dynamic_axes  = None,              # 锁定（禁止动态 shape）
)
```

| 字段 | 锁定项 | 锁定值 | 来源 |
| --- | --- | --- | --- |

## 八、审查流程

### 8.1 阶段审查

每个阶段结束时，执行以下流程：

1. **跑入口**：先执行 `python3 tools/verify_phase{N}.py`，记录退出码与 `outputs/verify/phase{N}.json`；
2. **自查**：对照本文档第三章「阶段门禁」逐条打勾，`BLOCKED` 项必须写明阻塞原因；
3. **交叉检查**：至少一人（非阶段执行者）核对打勾结果；
4. **冻结升格**：该阶段结束后，将「待确认」参数填入第七章对应位置，标注为「已冻结」；
5. **更新日志**：在本文档底部记录审查结果；
6. **通知下游**：如果有跨阶段红线的修改，通知受影响阶段的文档维护者。

### 8.2 契约修改

当需要修改已冻结的条目时：

1. **提出**：说明原因（官方规则变化 / 实验证伪 / 环境不可抗力）；
2. **评估**：列出受影响的下游阶段与产出物；
3. **执行**：修改本文档 + 受影响阶段文档 + 代码；
4. **记录**：更新日志追加「修改：[原因] → [新值]」。

### 8.3 审查记录模板

```markdown
## 审查记录 {YYYY-MM-DD}

**阶段**：阶段 X
**审查人**：...
**结果**：通过 / 不通过

**门禁**：
- [ ] GX-01 ...
- [ ] GX-02 ...
- 退出码：{0/1/2}，`BLOCKED` 项：...

**冻结**：
- {参数名}: {冻结值}

**待办**：
- [ ] ...
```
